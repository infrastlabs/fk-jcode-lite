# Jcode Swarm 多智能体使用指南

> 基于 v0.79.1 代码、仓库文档（`SWARM_ARCHITECTURE.md` / `SWARM_TASK_GRAPH.md` / README）及 jcode.sh 官网综合整理（2026-08-21）

---

## 一、什么是 Swarm

Jcode 的多智能体协调系统。官网定位："**Stop using git worktrees, start using swarms.**"——单个代理在搜索空间中走一条路径，swarm 并行搜索多条路径，同时让每个代理感知共享仓库的变化。

核心能力（官网/README）：

- 在同一仓库生成两个或多个代理，服务器自动管理实现原生协作
- **文件读取跟踪**：代理 A 编辑了代理 B 已读过的文件（脚下代码变动），服务器通知 B；B 可忽略或检查 diff 确认无冲突
- 消息能力：DM 单个代理、广播给服务器上所有代理、或仅广播给该仓库工作的代理
- 代理可自主生成自己的 swarm（`swarm` 工具），主代理变为协调器，生成代理变为工作者；分组、消息频道、完成状态等全部自动管理
- 可 headless（无头）或有头（headed）运行
- 官方演示：20 个代理并行

### 两种编排模式（一个引擎，两种预设）

> 来源：`SWARM_TASK_GRAPH.md`——**light 模式只是深度模式关掉结构压力并调小上限**。同一个 DAG 引擎、调度器、边缘数据流、成员上限机制，只有严格机制（强制分解+批判/验证门禁+递归）和成员上限不同。

| 维度 | Deep（全面深度） | Light（扇出） |
|-----------|------------------------------------------|---------------------|
| 目标 | 不放过任何角落 | 并行化追求速度/质量 |
| 形状 | 递归、自我加深的树 | 基本扁平，单层扇出 |
| 分解 | 强制（默认 composite） | 可选，代理自选 |
| 批判/验证门禁 | 任何节点关闭前必须经过 | 关闭（或最多一次可选终检） |
| 递归 | 鼓励，深度无上限 | 禁止（仅根可生成） |
| 交接产物 | 完整类型化 schema，含 `what_i_did_not_check` | 轻量，可自由格式 |
| 成员上限 | 最高 1000 代理 | 小（如 4-16 workers） |
| 成本/延迟 | 高、刻意 | 低、快 |

**触发**：`/effort swarm`（light 扇出）/ `/effort swarm-deep`（深度任务图）

## 二、触发激活方式（3 种）

### 1. 设置推理力度 sentinel

```
/effort swarm          # max 推理 + swarm 编排（light fan-out）
/effort swarm-deep     # max 推理 + 实时任务图（deep task graph，Beta）
```

swarm/swarm-deep 是 Jcode UI 哨兵值（非提供商推理等级），在 TUI 内映射为 max 推理并注入 swarm 编排指令。系统提示（`SWARM_EFFORT_DIRECTIVE`）会引导代理：对非平凡任务，使用 `swarm` 工具生成并行代理执行任务并收集报告，而不是单线程自行完成。

### 2. 直接调用 swarm 工具

在会话中指示模型调用 `swarm` 工具（`communicate` 的别名），action 指定操作：

```json
{"action": "spawn", "label": "api reviewer", "prompt": "审查 ...", "model": "gpt-5.5", "effort": "low"}
```

### 3. 编辑路由提示

```
/swarm-prompt
```

**UI 入口**：`Alt+N` 打开全页实时 Swarm 面板（所有权树、动画状态、详情活动）。TUI 另有 swarm 信息小部件（代理图视图）和计划信息小部件（任务 DAG + 检查点）。

## 三、架构模型（DAG 优先）

> 来源：`SWARM_TASK_GRAPH.md`——当前方向，已部分实现（DAG 引擎、deep/light 模式、门禁、扩展机制、子树广播已上线；频道/共享上下文弃用迁移进行中）

### 核心重构：任务 DAG 成为主要抽象

- 声明带依赖边和每节点配置的任务图；调度器走 DAG：依赖完成后节点变为可运行，分配给工作者（复用或生成），完成后自动解锁后代
- **代理是工作者池中的可替换劳动者**，不是需要微观管理的实体
- 协调器/工作区管理者角色降级为**调度策略**，不再是用户可见概念

### 所有权树叠加依赖图（无锁写入）

- 写入按所有者分区：只能在**自己拥有的节点**下添加子节点，两个所有者永不写同一区域——消除协调器瓶颈且无需锁
- 图仍是单一服务器所有、版本化的真相源（复用 `VersionedPlan`），但变更变为追加式操作（加节点、加边、完成节点），服务端验证无环+所有权
- 新边只能指向**已存在的上游节点**，从构造上保持无环

### 节点类型

**按命运（运行时才决定，草稿时无需声明）**：

- **Atomic（原子）**：工作者直接执行任务并写交接产物
- **Composite（复合）**：代理认为任务太大，将节点分解为自己的子 DAG，原节点成为 join/合成点（等所有子节点完成 → 重新唤醒 → 读子产物 → 写合成输出）；所有者只做 map-then-reduce，不亲自执行叶子工作

**按终端动作**：

| 类型 | 产物（输出） | "完成"契约 |
|-----------|------------------|-------------|
| `explore` | 调查结果 | 通过批判门禁 |
| `implement` | diff / commit 引用 + 变更说明 | 通过验证门禁 |
| `verify` | 通过/失败 + 具体失败项 | 检查已执行 |
| `fix` | 补丁 | 重新验证通过 |

验证失败会生成 fix 节点（更多图），正好对应批判生成 gap 节点——让系统"行动并自我纠正"而非只描述。

### 数据流：依赖边即数据通道

- 完成时每个节点存储结构化**交接产物**；下游任务变为可运行（依赖全部完成）时，调度器组装输入 = 任务自身提示 + 所有依赖产物的合并
- 产物默认**按引用而非按值**："我在 `crates/foo/api.rs` 建了 API，类型 X/Y，提交 `abc123`"——仓库+git 是共享介质，下游自己读文件；只有决策/设计/分析等不在仓库中的内容才内嵌传值，保持上下文小
- 复合节点 = 分解-再合成（map-reduce），父节点绝不简单拼接子节点噪音，而是产出干净摘要给下一层

## 四、配置项

### TOML 配置（`~/.jcode/config.toml` 的 `[agents]` 段）

```toml
[agents]
# 生成代理默认模型："inherit"/"coordinator"（继承生成它的会话）或具体模型名
# Env: JCODE_SWARM_MODEL
# swarm_model = "inherit"

# 生成方式：
#   "inline"   - 进程内（无窗口），协调器内显示实时图库视口（默认）
#   "visible"  - 打开有头终端窗口（别名 "headed"）
#   "headless" - 进程内创建，无终端窗口
#   "auto"     - 先尝试 visible，打不开窗口则回退 headless
# 工具每次调用的 spawn_mode 参数可覆盖此设置
# Env: JCODE_SWARM_SPAWN_MODE
swarm_spawn_mode = "inline"

# 单个 swarm 的最大并发工作代理数（RAM 安全预算）
# 0 = 关闭此守卫，仅剩 1000 的绝对硬顶；light 模式使用更小的固定扇出
# Env: JCODE_SWARM_MAX_CONCURRENT_AGENTS
swarm_max_concurrent_agents = 32

# 内联 swarm 图库带最大占用聊天高度百分比（1-90），默认 40
# swarm_gallery_max_pct = 40

# 内联 swarm 条布局：
#   "vertical"   - 每代理一行（会话图标 + 状态 + 任务），超出显示 "+N more"（默认）
#   "horizontal" - 所有代理作为 chip 排成一行
# Env: JCODE_SWARM_STRIP_LAYOUT
# swarm_strip_layout = "vertical"
```

### 顶层配置

```toml
swarm = true                # 功能开关
swarm_panel_focus = "alt+n" # Swarm 面板快捷键
```

### 路由提示覆盖（关键配置）

这个文件本身就是 swarm 的"配置"——路由策略以提示形式传给模型：

- 全局：`~/.jcode/swarm-prompt.md`
- 项目级：`./.jcode/swarm-prompt.md`（优先）

内置默认内容（`crates/jcode-base/src/prompt/swarm_prompt.md`）：

- 默认工作代理模型：Fable 5（Anthropic API 路由 `claude-api:claude-fable-5`）
- 实现类任务：`gpt-5.5` + `effort: "low"`
- 设计/调查/调试/审查/验证：`claude-api:claude-fable-5`
- 上下文提取/批量阅读/总结：`gpt-5.5` + `effort: "none"`
- 路由不可用或不确定时省略 `model`，让工作代理继承协调器模型
- 所有 `spawn` 必须传 `label`（明确拒绝缺失/空白）

## 五、swarm 工具动作全集

> 来源：`communicate.rs` 实现 + 本会话工具定义

### 生成与生命周期

| 动作 | 说明 | 关键参数 |
|---------|-----------|-------------|
| `spawn` | 生成新工作代理 | `label`（必填）、`prompt`/`initial_message`、`model`、`effort`、`spawn_mode` |
| `stop` | 停止代理（自己子树内；外部需 `force=true`） | `to_session`/`target_session`、`force` |
| `wake` | 唤醒代理 | `to_session` |
| `resume` | 唤醒并恢复 | `to_session` |
| `retry` | 重试失败任务（保留同一受派者） | `task_id` |
| `salvage` | 抢救搁浅任务（保留任务进展上下文重派） | `task_id` |
| `reassign` | 重新分配任务（移到另一个现有代理） | `task_id`、`to_session` |
| `replace` | 替换失效代理（安全状态检查后换新受派者） | `to_session` |

### 消息通信

| 动作 | 说明 | 关键参数 |
|---------|-----------|-------------|
| `message` | 向单个代理发消息 | `to_session`、`message` |
| `dm` | 私信（别名 `dm_session`/`whisper`，首选例外通道） | `to_session`、`message` |
| `broadcast` | 子树广播（别名 `announce`，只达发送者的生成子树；协调器保有全 swarm 逃生门） | `message` |
| `read` | 读取收件箱 | `limit` |
| `share` / `share_append` | 共享/追加共享上下文（不鼓励，优先仓库+类型化节点产物） | `key`、`value` |
| `channel` | 频道操作（不鼓励，优先 DM 和任务图产物） | `channel` |
| `subscribe_channel` / `unsubscribe_channel` | 订阅/退订频道 | `channel` |
| `channel_members` | 查看频道成员 | `channel` |
| `list_channels` | 列出频道 | - |

### 计划管理（仅根协调器可操作，共享计划只有一个）

| 动作 | 说明 | 关键参数 |
|---------|-----------|-------------|
| `propose_plan` | 提议计划更新 | `plan_items`、`reason` |
| `approve_plan` | 批准计划 | `task_id`/`node_id` |
| `reject_plan` | 拒绝计划 | `reason` |
| `plan_status` | 查看计划状态 | - |
| `resync_plan` | 重新同步/附加计划 | `task_id` |
| `task_graph` | 任务图操作（构建/查看） | `nodes`、`concurrency_limit` |
| `expand_node` | 展开任务节点（扩展你拥有的节点） | `node_id`、`nodes` |
| `complete_node` | 完成任务节点并上交产物 | `node_id`、`artifact` |
| `inject_gap` | 注入缺口（门控评审） | `gate_id`、`nodes` |

### 任务编排

| 动作 | 说明 | 关键参数 |
|---------|-----------|-------------|
| `assign_task` | 分配任务（可自动选下一个可运行任务，缺人时生成后备） | `task_id`、`prefer_spawn` |
| `assign_next` | 自动分配下一个任务 | - |
| `fill_slots` | 填充并发槽位 | `concurrency_limit` |
| `run_plan` | 运行整个计划 | `background`、`retain_agents` |
| `start` / `start_task` | 启动任务 | `task_id` |
| `await_members` | 等待代理完成（可追踪后期加入者） | `session_ids`、`mode`（all/any）、`timeout_minutes`、`target_status` |
| `cleanup` | 清理已结束代理 | `retain_agents` |

### 查询与汇报

| 动作 | 说明 | 关键参数 |
|---------|-----------|-------------|
| `list` | 列出代理（`members`/`roster`） | - |
| `list_models` | 查看可用模型/路由 | - |
| `status` | 代理状态快照（无锁，忙碌时也可用） | `to_session` |
| `summary` | 短活动流（工具调用意图、简要结果、可选暴露的思考） | `limit`、`to_session` |
| `read_context` | 完整上下文读取（重型操作，谨慎使用以防上下文膨胀） | `to_session` |
| `report` | 汇报结果 | `message`、`status`、`validation`、`follow_up`、`tldr` |

## 六、角色、生命周期与通信

### 角色（DAG 重构前的代理优先模型）

| 角色 | 职责 |
|---------|---------|
| **协调器（Coordinator）** | 持有共享计划槽位：创建计划、分配范围、审批更新、广播计划更新。仅根会话可担任，不会在空/过期时被深度后代抢占。不执行 merge/集成 |
| **工作区管理者（Worktree Manager）** | 拥有单个 worktree 范围：了解完整计划与范围，负责该范围完成后的集成 |
| **代理（Agent）** | 并行执行任务：接收完整计划+范围指令，发现问题时提议计划更新，通过 DM/频道直接协调 |

> 注：DAG 重构后，这些角色降级为**调度策略**，不再是用户可见概念。

### 生命周期状态

`spawned`（已生成，未就绪）→ `ready`（收到计划与范围）→ `running`（执行中）→ `blocked`（阻塞）→ `completed`（完成等待新任务）/ `failed`（不可恢复错误）/ `stopped`（协调器关闭）/ `crashed`（异常退出）

### 完成报告策略

- 受协调器拥有的代理（`report_back_to_session_id`）必须以有用的最终助手响应结束每次工作轮，服务器自动转发该响应给协调器作为完成报告
- 报告应包含：结果/状态、变更或发现、执行的验证、阻塞项或后续步骤；不应只是 `done`、生命周期状态变化或工具转录
- 报告必填场景：spawn 提示、分配的计划任务、显式 start/wake/resume/retry 任务控制运行；失败时协调器仍收到失败生命周期通知
- 报告非必填：无提示的空闲 spawn、无 report-back 所有者的用户创建对等、运行中的普通状态广播、主动清理/停止空闲代理
- 完成/空闲代理收到通知不会自动恢复，除非协调器分配新工作/显式启动/唤醒/重生成

### 通信与软中断

- 所有代理间通信以**通知**形式投递（DM、频道消息、广播、计划更新、意图通知、生命周期事件）
- 通知作为软中断排队，在安全点注入运行中的代理，所以消息可在轮次中交错而不必开启新轮
- 首选 DM；子树广播次之；话题频道和共享上下文键不鼓励（优先仓库 + 类型化节点产物）

### 冲突处理（无锁，乐观）

- 系统默认乐观（无锁）
- **文件触达（file touch）通知**用于冲突检测：代理 A 编辑了 B 读过的文件时通知 B
- 冲突应促使相关代理直接 DM/频道沟通解决，不经过协调器

### Worktree 用法

- 可选：仅当隔离有帮助时使用（大重构、高风险变更、分歧依赖）
- 多数工作留主工作区；一个 worktree 可被多个代理共享
- 每个 worktree 有 Worktree Manager 负责集成；每个 worktree 分配逻辑 `swarm_id`，使通信、计划更新和 UI 视图跨同 swarm 所有 worktree

## 八、快速上手

```text
1. 在会话中设置深度模式：
   /effort swarm-deep

2. 给模型一个复杂任务（它会自动用 swarm 工具分解）：
   "重构这个模块，拆成3个独立任务并行执行"

   Alt+N 打开实时 Swarm 面板

5. 需要调整代理模型策略时：
   /swarm-prompt
```

## 九、注意事项

- **标签必填**：`spawn` 必须提供简短 `label`，否则拒绝执行
- **并发预算**：默认 32 并发（light 模式更小），完成/停止的代理释放槽位；硬顶 1000
- **深度模式专属**：递归生成只在 `swarm-deep` 根的会话树内允许；light 模式仅根可生成
- **计划操作门控**：`assign_task`/`approve_plan`/`reject_plan` 等计划操作只允许根协调器（共享计划只有一个）
- **长消息**：超过折叠阈值的 message/report 需要 `tldr`，在收件人 UI 折叠显示
- **模型覆盖**：`model`/`effort` 参数优先级高于 `agents.swarm_model` 配置
- **记忆作用域**：swarm 工作代理能看到生成它的会话的项目记忆（非隔离存储）
- **记忆侧车（memory sidecar）**：独立的 LLM 精度判定器，专职处理记忆相关性判定与提取，随主会话并行运行（区别于 swarm 工作代理本身）
- **工作目录绑定**：swarm ID 和 MCP 发现绑定到接受的工作目录（v0.59 修复跨目录混淆）
- **状态读取分级**：状态快照（无锁、忙碌可用）< 摘要读取（轻）< 完整上下文读取（重型，谨慎）
- **搁浅恢复**：搁浅的代理延续被恢复而非静默卡住（v0.59）；死代理任务被回收并汇报协调器；run_plan 遇凭证失败波次暂停并展示修复方案
