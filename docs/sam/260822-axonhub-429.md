# AxonHub 对接请求高失败率分析（5 次成功 1 次）

> 分析时间：2026-08-22
> 分析对象：`jcode`（v0.79.1，branch `sam-custom`）对接本地 `axonhub 1.0.0-beta6` 代理（`http://localhost:8090/v1`）
> 数据来源：`~/.jcode/logs/jcode-2026-08-20.log`、`jcode-2026-08-21.log`、`jcode-2026-08-22.log`、`jcode-2026-08-23.log`、`~/.jcode/config.toml`、axonhub 进程状态、直连 curl 测试

---

## 一、结论

请求“5 次成功 1 次”的直接原因：**本地 axonhub 代理对约一半以上的请求直接返回 HTTP 429（Too Many Requests）**，并非超时、断连或 jcode 自身故障。jcode 按配置对单次请求最多重试 8 次，多数情况下在第 3-6 次尝试时才落到非 429 的窗口，于是呈现为“每 5 次请求成功 1 次”。

429 的根源在 axonhub 所代理的上游（免费/聚合模型池）的 **QPS / 配额限流**，且随上游高峰时段波动。

---

```
  └─ POST http://localhost:8090/v1/chat/completions   (open-ai-compatible)
       └─ axonhub 1.0.0-beta6 (pid 612777, Go 二进制，SQLite 记账)
            └─ 上游 https: 47.92.141.220:443 / 180.184.249.196:443
```

直连验证（分析时点，代理健康）：

| 测试 | 结果 |
|------|------|
| `GET /v1/models` | HTTP 200，11ms |
| `POST /chat/completions`（非流式） | HTTP 200，0.3s |
| `POST /chat/completions`（`stream:true`） | HTTP 200，约 1s，正常流出 2.4KB |

即：代理本身在线、本地网络通路正常，失败是**间歇性限流**，不是连不上。

| 模型 | 429 | 200 | 失败率 |

所有免费/聚合模型（`st/`、`mscope/`、`gitee/`、`ocfree/` 前缀）都受限，不是单一模型问题。

### 3.4 单回合内的重试消耗（`jcode-2026-08-22.log` + daemon 侧日志）

- turn 49：单回合 10 次 API 调用（`KV_CACHE_USAGE: turn=49 call=1..10`），期间 5-6 次 429 后才 200。
- turn 51：00:27:20 → 00:31:25，约 4 分钟，attempt 序列 `200 → 429 → 200 → 429… → 200(Done)`。
- 每回合 message 数随失败重试增长（每次失败追加错误+重试提示约 2 条消息），输入 token 也随之膨胀。

### 3.5 个别“卡住”体感的来源

429 需要 **4-13 秒**才返回（本地代理在等上游判定，如 `5057ms / 9170ms / 12948ms / 14870ms`）。期间 TUI 状态为 `Streaming…` 且 `streaming_text_len=0`，用户看起来是“流式但不出字”，随后才进入重试退避：

- 退避：`retry_backoff_delay`：1s 起步指数翻倍（`1s→2s→4s→8s…`），封顶 `retry_backoff_cap_secs=30`；若响应带 `Retry-After` 最多等待 60s。
- 一次失败“体感卡住”几十秒，一个回合耗 3-4 分钟很正常。

### 3.6 与 maki / zerostack 的对照（关键差异）

用户实测：**同样的 axonhub 代理（`http://sam-dev.local:8090/v1`，解析到 127.0.0.1）、相同的 `AXONHUB_API_KEY`，走 maki/zerostack 时各模型基本次次成功**。差异不在代理本身，而在请求负载与模型路由：

| 维度 | jcode | maki / zerostack |
|------|-------|------------------|
| 单请求输入规模 | median **71k tokens**，p90 **154k**（失败回合 160k-180k；会话累计 1200 万+） | 平均 **14k tokens**（log 实测 5132 次请求 avg=14009） |
| 请求模型 | `mscope/glm-5.2`、`st/glm-5.2` 等免费池（429 率 56%-70%） | 主力 `st/sensenova-6.7-flash-lite`（商用渠道，配额足） |
| 429 出现 | 52% 尝试（576/1111） | 12.5% 尝试（729 次 retry 事件 / 5115 次成功响应），靠 1-6s 短退避快速消化 |

maki 日志里能直接看到 429 的具体错误体（与 jcode 同一个代理转发）：

```json
{"error":{"code":"8","message":"rpm exhausted","type":"quota_exceeded_error"}}
{"error":{"code":"insufficient_quota","message":"Workspace allocated quota exceeded, please increase your quota limit.","type":"invalid_request_error"}}
```

`rpm exhausted` / 工作区配额 = **上游按“每分钟请求数 / 工作区配额”限流**。机制解释：

1. jcode 单请求 71k-180k tokens，体量是 maki 的 5-15 倍；上游每条请求处理耗时更长，占住限流窗口更久。
2. jcode 重试间隔 5-10s，第 1-5 次尝试基本都落在同一个 60s RPM 窗口内，全部 429；等到窗口重置（约 1 分钟后）才出 200。这和日志实测完全吻合：**首次 429 到成功 200 之间恒为 60-75s**（如 22:05:21 → 22:06:25 = 64s；00:29:02 → 00:30:15 ≈ 73s）。
3. maki 小请求几乎不触发窗口，偶发 429 也凭短退避迅速成功，用户感知“基本次次成功”。

结论：根因是 **上游免费渠道的 RPM/工作区配额限流被 jcode 的大请求 + 密集重试放大**，不是 jcode 客户端代码或网络的问题。

## 五、jcode 侧行为解释

- 429 在 `is_retryable_error` 中被明确判为可重试（正确）。
- `max_retries=8`、退避封顶 30s，最终通常能在 8 次内拿到 200，因此 `cross_provider_failover` 基本不触发。
- `providers.axonhub` 是自定义 `open-ai-compatible` 提供商，只有单一路由、单一账号：`same_provider_account_failover` 对它不生效，只能反复打同一个 8090。
- 无传输层错误（无 timeout / refused / reset / TLS 错误），网络配置无问题。

## 六、建议

1. **先切模型路由**（立竿见影）：maki 主力 `st/sensenova-6.7-flash-lite` 渠道配额足；jcode 模型清单里已有同系列的 `st/sensenova-6.8-flash-lite`（256k 上下文），把 `default_model` 切过去，或优先用 `st/deepseek-v4-flash`（48% 失败，免费池里最低）。
2. **压缩单请求体量**（治本方向）：当前 median 71k / p90 154k tokens，远大于 maki 的 14k。调低 `openai_native_compaction_threshold_tokens`（200000 → 80000-120000）让长会话更早 compaction，或长任务中途开新会话，把单请求压到 30k-60k 内，减少对 RPM 窗口的占用。
3. **主因仍在上游配额**：`rpm exhausted` / `insufficient_quota` 是免费渠道限额。去 axonhub 后台确认当前 API key 的 QPS / 工作区配额，高峰期错峰（下午-晚间最差，凌晨基本全成功），或换付费档位。
4. **jcode 侧参数**（`~/.jcode/config.toml` `[provider]`）：
   - `retry_backoff_cap_secs`：30 → 60（让重试跳过 60s 限流窗口，减少窗口内空转）。
   - 保持 `max_retries = 8`、`stream_idle_timeout_secs = 180`。
5. **升级 axonhub**：当前 `1.0.0-beta6`（改动日志很短），关注新版是否改进 429 处理、支持多 key / 多上游负载分摊。
6. **验证手段**：直接在 axonhub 上压测同一批请求，统计 429 占比与上述数据对照；观察晚间与凌晨的差异。

## 八、切模型后首次响应仍然偏慢的分析（追加 2026-08-22 17:41）

切到 `st/sensenova-6.8-flash-lite` 后，请求不再 429（见 §四：连发 5 次 5/5 全 200，直测 TTFH 0.37-0.74s），但**首次响应体感仍有 4-15s 延迟**，和 maki 侧 0.5s 首字有明显差距。原因不在 429，而在**jcode 每次请求的输入体量**。

### 8.1 实机日志（daemon `jcode-2026-08-21.log` 末段）

```

```

关键数据：

| 指标 | 值 | 说明 |
|------|-----|------|
| 每次请求 message 数 | 221-223 | 会话历史完整发送，未截断 |
| 每次请求 JSON 体积 | 511KB-521KB | `request_json_chars` |

### 8.2 与 maki 的对比（同为 sensenova 系列）

```
maki sensenova-6.7 input_tokens: median=19181, p90=2673, max=2503
```

jcode 每次 180k tokens vs maki 中位 19k tokens，**差约 10 倍**。这就是首字延迟的根因：**不是代理限流，是上游处理 180k tokens 上下文本身需要 4-5s**。

### 8.3 用 curl 直接压代理，按 payload 大小分段验证

直测 `http://localhost:8090/v1/chat/completions`（`st/sensenova-6.8-flash-lite`），结果：

| payload 规模 | TTFH | 说明 |
|------|------|------|
| 10 token ping | **0.42s** | 之前 curl 直测 0.5s，基线 |
| 198KB（221 msg + 32 tools，长 tool output） | **6.5s** | 逼近 jcode 真实规模 |

结论：**axonhub 上游对 5-200KB 量级的请求，TTFH 与 payload 体量呈近线性关系**；10KB 级 ~0.4s，200KB 级 ~6.5s。和 jcode 实测的 4-8s HTTP 建立耗时吻合。

### 8.4 为什么不是 4s 而是 15s

用户体感的 15s ≈ `jcode 前置处理` + `HTTP 建立 4-5s` + `模型 thinking 前段`。拆分：

1. **jcode 侧前置**：`prompt prefix estimate`、tool surface 收集、canonical input 日志、fingerprint 计算，约 0.03-0.1s。
2. **HTTP 建立到 200**：4-8s（上游处理 180k tokens 上下文）。
3. **模型 thinking**：senseno 系列是 reasoning 模型，首 token 前会先输出 `reasoning_content`，这段在 log 里被 SSE 流拉走，TUI 显示仍在 "Streaming 0 字"。
4. **TUI render 延迟**：`TUI_SLOW_FRAME` 日志中曾记录到 `prepare_ms=50-70ms`，不是主因。

所以 15s 里，**8-12s 是上游在吃 180k tokens 上下文，2-4s 是模型 thinking，1-2s 是 jcode 前置 + TUI**。

### 8.5 压缩阈值为何没生效（100000 阈值 vs 180k 实际输入）

`openai_native_compaction_threshold_tokens = 100000` 是"触发条件"，但触发后压缩的是**中间轮次**（不压缩首尾工具调用），且阈值是按"当前会话已累积 token 数"估算的，不是按"单次请求体"。221 条消息的会话里，`system(1573) + tools(11544) + 历史 180k - system/tools ≈ 167k` 才是会话消息部分；167k > 100k 应已触发压缩，但日志显示 `cache_supported=false cache_control_added=false`，且 `prefix_matches=true` 说明上游不支持前缀缓存，jcode 只能把"压缩后仍超限"的消息发出去。**核心是：jcode 的 compaction 阈值按会话累积，不是按单请求，阈值 100k 在长会话里仍然塞不下**。

### 8.6 立即可试的缓解措施

1. **再降 compaction 阈值到 50000**：`openai_native_compaction_threshold_tokens = 50000`，让长会话更早压缩，把单请求压到 50k-80k tokens 内，TTFH 应能压到 2-3s。
2. **新开会话**：当前 `session_puppy_*` 累积 221 条消息；新 session 首条消息 TTFH 会立刻回到 0.5s。
3. **换非 thinking 模型**：senseno 系列的 `reasoning_content` 在首字前就占几秒；如果要更快首字，换 `st/deepseek-v4-flash` 或 `mscope/deepseek-v4-flash`（无 thinking 前缀）。
4. **关闭 tool surface 全量发送**：`tool_count=32`、`tools_json_chars=46519` 每次固定开销，如果能按需裁剪到 10 个核心工具，能省 30% 的 system+tools tokens。

> 注：8-12s 的上游处理开销是"吃上下文"的本质限制，不靠客户端修改能彻底消除；只能靠压缩历史、裁剪工具、或者换支持 prefix cache 的上游。

### 8.7 新开会话验证（追加 2026-08-22 17:48）

用户新开一个 session 测试，**首条消息 0.5-2s 即可回执**，与 maki 侧基线一致。这直接验证了 §八 的核心判断：

| 条件 | 输入规模 | 首字耗时 |
|------|---------|---------|
| 老会话（221 条消息） | 180k tokens | 4-15s |
| 新会话（首条消息） | 少量 tokens | 0.5-2s |

结论：**延迟根因在会话历史累积量，不是代理、网络或模型本身**。新会话无历史包袱，TTFH 立刻回到正常基线。

**后续优化方向确定**：

1. 核心问题是 compaction 阈值按"会话累积 token"估算，而非按"单次请求体 tokens"限制，导致 221 条消息累积到 180k 时仍未触发强制压缩。
2. 建议把 `openai_native_compaction_threshold_tokens` 降到 50000，并观察是否能让单请求稳定压到 80k tokens 以下。
3. 如果阈值仍不够激进，需要从代码层面调整 compaction 策略（见 §八 8.5 说明），让"压缩后单次请求输入"成为硬约束，而不是"会话累积超过阈值时压缩"的软约束。

> 本节由用户实测反馈补充，验证了 §八 8.6 第 2 条建议（新开会话）的有效性。

### 8.8 代码层分析：为什么 `openai_native_compaction_threshold_tokens` 降了却没用（追加 2026-08-22 17:52）

**结论：`openai_native_compaction_threshold_tokens` 并非触发 jcode 压缩的条件**，只是控制发送请求时 `prefixItems` 参数的数量上限。真正决定 jcode 是否压缩的，是 `crates/jcode-compaction-core/src/lib.rs` 里的三个硬编码常量：

| 常量 | 值 | 含义 |
|------|-----|------|
| `DEFAULT_TOKEN_BUDGET` | 200_000 | 单会话 token 预算 |
| `COMPACTION_THRESHOLD` | 0.80 | 达到预算 80% 触发压缩 |
| `CRITICAL_THRESHOLD` | 0.95 | 达到 95% 强制压缩 |

**实际触发点 = 200_000 × 0.80 = 160k tokens**。当前会话 180k 已超限，但实际执行压缩还受 4 层 gate 卡住：

1. `anti_signals_block`（`compaction.rs:463`）：已在压缩中、token 停滞、冷却期未满。
2. Proactive/semantic 模式各自的触发逻辑。
3. `min_samples`：至少需要 N 轮 token 快照才能开始投影。
4. `stall_window`：如果最近几轮 token 没增长，不触发。

**所以"降 `openai_native_compaction_threshold_tokens` 到 50000"不会生效，改的不是正确的杠杆。**

### 8.9 可行的代码改动方向（3 个选项）

**A. 最轻改：直接降 `DEFAULT_TOKEN_BUDGET`（`crates/jcode-compaction-core/src/lib.rs:6`）**

```diff
- pub const DEFAULT_TOKEN_BUDGET: usize = 200_000;
```

**C. 让 `native_compaction_threshold_tokens` 兼作硬约束**

在 `openai_provider_impl.rs:856` 附近取 `native_compaction_threshold_tokens` 作为 `token_budget` 的 cap：如果 provider 声明了 50000，强制 `budget = min(budget, 50000)`。这样改 `~/.jcode/config.toml` 一个值即可，和现有语义对齐。

推荐 **C**，改动最小、用户最易用。
