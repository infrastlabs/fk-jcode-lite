# AxonHub 对接请求高失败率分析（5 次成功 1 次）

> 分析时间：2026-08-22
> 分析对象：`jcode`（v0.79.1，branch `sam-custom`）对接本地 `axonhub 1.0.0-beta6` 代理（`http://localhost:8090/v1`）
> 数据来源：`~/.jcode/logs/jcode-2026-08-20.log`、`jcode-2026-08-21.log`、`jcode-2026-08-22.log`、`jcode-2026-08-23.log`、`~/.jcode/config.toml`、axonhub 进程状态、直连 curl 测试

---

## 一、结论

请求“5 次成功 1 次”的直接原因：**本地 axonhub 代理对约一半以上的请求直接返回 HTTP 429（Too Many Requests）**，并非超时、断连或 jcode 自身故障。jcode 按配置对单次请求最多重试 8 次，多数情况下在第 3-6 次尝试时才落到非 429 的窗口，于是呈现为“每 5 次请求成功 1 次”。

429 的根源在 axonhub 所代理的上游（免费/聚合模型池）的 **QPS / 配额限流**，且随上游高峰时段波动。

---

## 二、请求链路与现状验证

```
jcode (TUI/daemon)
  └─ POST http://localhost:8090/v1/chat/completions   (open-ai-compatible)
       └─ axonhub 1.0.0-beta6 (pid 612777, Go 二进制，SQLite 记账)
            └─ 上游 https: 47.92.141.220:443 / 180.184.249.196:443
```

直连验证（分析时点，代理健康）：

| 测试 | 结果 |
|------|------|
| `GET /v1/models` | HTTP 200，11ms |
| `POST /chat/completions`（非流式） | HTTP 200，0.3s |
| `POST /chat/completions`（`stream:true`） | HTTP 200，约 1s，正常流出 2.4KB |

即：代理本身在线、本地网络通路正常，失败是**间歇性限流**，不是连不上。

### 3.3 分模型（08-21 全天）

| 模型 | 429 | 200 | 失败率 |
|------|-----|-----|--------|
| `st/glm-5.2` | 165 | 72 | 70% |
| `mscope/glm-5.2` | 115 | 92 | 56% |
| `st/deepseek-v4-flash` | 298 | 321 | 48% |

所有免费/聚合模型（`st/`、`mscope/`、`gitee/`、`ocfree/` 前缀）都受限，不是单一模型问题。

### 3.4 单回合内的重试消耗（`jcode-2026-08-22.log` + daemon 侧日志）

- turn 49：单回合 10 次 API 调用（`KV_CACHE_USAGE: turn=49 call=1..10`），期间 5-6 次 429 后才 200。
- turn 51：00:27:20 → 00:31:25，约 4 分钟，attempt 序列 `200 → 429 → 200 → 429… → 200(Done)`。
- 每回合 message 数随失败重试增长（每次失败追加错误+重试提示约 2 条消息），输入 token 也随之膨胀。

### 3.5 个别“卡住”体感的来源

429 需要 **4-13 秒**才返回（本地代理在等上游判定，如 `5057ms / 9170ms / 12948ms / 14870ms`）。期间 TUI 状态为 `Streaming…` 且 `streaming_text_len=0`，用户看起来是“流式但不出字”，随后才进入重试退避：

- 退避：`retry_backoff_delay`：1s 起步指数翻倍（`1s→2s→4s→8s…`），封顶 `retry_backoff_cap_secs=30`；若响应带 `Retry-After` 最多等待 60s。
- 一次失败“体感卡住”几十秒，一个回合耗 3-4 分钟很正常。

### 3.6 与 maki / zerostack 的对照（关键差异）

用户实测：**同样的 axonhub 代理（`http://sam-dev.local:8090/v1`，解析到 127.0.0.1）、相同的 `AXONHUB_API_KEY`，走 maki/zerostack 时各模型基本次次成功**。差异不在代理本身，而在请求负载与模型路由：

| 维度 | jcode | maki / zerostack |
|------|-------|------------------|
| 单请求输入规模 | median **71k tokens**，p90 **154k**（失败回合 160k-180k；会话累计 1200 万+） | 平均 **14k tokens**（log 实测 5132 次请求 avg=14009） |
| 请求模型 | `mscope/glm-5.2`、`st/glm-5.2` 等免费池（429 率 56%-70%） | 主力 `st/sensenova-6.7-flash-lite`（商用渠道，配额足） |
| 429 出现 | 52% 尝试（576/1111） | 12.5% 尝试（729 次 retry 事件 / 5115 次成功响应），靠 1-6s 短退避快速消化 |

maki 日志里能直接看到 429 的具体错误体（与 jcode 同一个代理转发）：

```json
{"error":{"code":"8","message":"rpm exhausted","type":"quota_exceeded_error"}}
{"error":{"code":"insufficient_quota","message":"Workspace allocated quota exceeded, please increase your quota limit.","type":"invalid_request_error"}}
```

`rpm exhausted` / 工作区配额 = **上游按“每分钟请求数 / 工作区配额”限流**。机制解释：

1. jcode 单请求 71k-180k tokens，体量是 maki 的 5-15 倍；上游每条请求处理耗时更长，占住限流窗口更久。
2. jcode 重试间隔 5-10s，第 1-5 次尝试基本都落在同一个 60s RPM 窗口内，全部 429；等到窗口重置（约 1 分钟后）才出 200。这和日志实测完全吻合：**首次 429 到成功 200 之间恒为 60-75s**（如 22:05:21 → 22:06:25 = 64s；00:29:02 → 00:30:15 ≈ 73s）。
3. maki 小请求几乎不触发窗口，偶发 429 也凭短退避迅速成功，用户感知“基本次次成功”。

结论：根因是 **上游免费渠道的 RPM/工作区配额限流被 jcode 的大请求 + 密集重试放大**，不是 jcode 客户端代码或网络的问题。

## 四、jcode 侧行为解释

- 429 在 `is_retryable_error` 中被明确判为可重试（正确）。
- `max_retries=8`、退避封顶 30s，最终通常能在 8 次内拿到 200，因此 `cross_provider_failover` 基本不触发。
- `providers.axonhub` 是自定义 `open-ai-compatible` 提供商，只有单一路由、单一账号：`same_provider_account_failover` 对它不生效，只能反复打同一个 8090。
- 无传输层错误（无 timeout / refused / reset / TLS 错误），网络配置无问题。

## 五、建议

1. **先切模型路由**（立竿见影）：maki 主力 `st/sensenova-6.7-flash-lite` 渠道配额足；jcode 模型清单里已有同系列的 `st/sensenova-6.8-flash-lite`（256k 上下文），把 `default_model` 切过去，或优先用 `st/deepseek-v4-flash`（48% 失败，免费池里最低）。
2. **压缩单请求体量**（治本方向）：当前 median 71k / p90 154k tokens，远大于 maki 的 14k。调低 `openai_native_compaction_threshold_tokens`（200000 → 80000-120000）让长会话更早 compaction，或长任务中途开新会话，把单请求压到 30k-60k 内，减少对 RPM 窗口的占用。
3. **主因仍在上游配额**：`rpm exhausted` / `insufficient_quota` 是免费渠道限额。去 axonhub 后台确认当前 API key 的 QPS / 工作区配额，高峰期错峰（下午-晚间最差，凌晨基本全成功），或换付费档位。
4. **jcode 侧参数**（`~/.jcode/config.toml` `[provider]`）：
   - `retry_backoff_cap_secs`：30 → 60（让重试跳过 60s 限流窗口，减少窗口内空转）。
   - 保持 `max_retries = 8`、`stream_idle_timeout_secs = 180`。
5. **升级 axonhub**：当前 `1.0.0-beta6`（改动日志很短），关注新版是否改进 429 处理、支持多 key / 多上游负载分摊。
6. **验证手段**：直接在 axonhub 上压测同一批请求，统计 429 占比与上述数据对照；观察晚间与凌晨的差异。
