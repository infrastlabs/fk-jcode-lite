# AxonHub 对接请求高失败率分析（5 次成功 1 次）

> 分析时间：2026-08-22
> 分析对象：`jcode`（v0.79.1，branch `sam-custom`）对接本地 `axonhub 1.0.0-beta6` 代理（`http://localhost:8090/v1`）
> 数据来源：`~/.jcode/logs/jcode-2026-08-20.log`、`jcode-2026-08-21.log`、`jcode-2026-08-22.log`、`jcode-2026-08-23.log`、`~/.jcode/config.toml`、axonhub 进程状态、直连 curl 测试

---

## 一、结论

请求“5 次成功 1 次”的直接原因：**本地 axonhub 代理对约一半以上的请求直接返回 HTTP 429（Too Many Requests）**，并非超时、断连或 jcode 自身故障。jcode 按配置对单次请求最多重试 8 次，多数情况下在第 3-6 次尝试时才落到非 429 的窗口，于是呈现为“每 5 次请求成功 1 次”。

429 的根源在 axonhub 所代理的上游（免费/聚合模型池）的 **QPS / 配额限流**，且随上游高峰时段波动。

---

## 二、请求链路与现状验证

```
jcode (TUI/daemon)
  └─ POST http://localhost:8090/v1/chat/completions   (open-ai-compatible)
       └─ axonhub 1.0.0-beta6 (pid 612777, Go 二进制，SQLite 记账)
            └─ 上游 https: 47.92.141.220:443 / 180.184.249.196:443
```

直连验证（分析时点，代理健康）：

| 测试 | 结果 |
|------|------|
| `GET /v1/models` | HTTP 200，11ms |
| `POST /chat/completions`（非流式） | HTTP 200，0.3s |
| `POST /chat/completions`（`stream:true`） | HTTP 200，约 1s，正常流出 2.4KB |

即：代理本身在线、本地网络通路正常，失败是**间歇性限流**，不是连不上。

规律：**晚间/下午评分率明显高于凌晨**，指向上游服务容量/配额随高峰期耗尽。

### 3.3 分模型（08-21 全天）

| 模型 | 429 | 200 | 失败率 |
|------|-----|-----|--------|
| `st/glm-5.2` | 165 | 72 | 70% |
| `mscope/glm-5.2` | 115 | 92 | 56% |
| `st/deepseek-v4-flash` | 298 | 321 | 48% |

所有免费/聚合模型（`st/`、`mscope/`、`gitee/`、`ocfree/` 前缀）都受限，不是单一模型问题。

### 3.4 单回合内的重试消耗（`jcode-2026-08-22.log` + daemon 侧日志）

- turn 49：单回合 10 次 API 调用（`KV_CACHE_USAGE: turn=49 call=1..10`），期间 5-6 次 429 后才 200。
- turn 51：00:27:20 → 00:31:25，约 4 分钟，attempt 序列 `200 → 429 → 200 → 429… → 200(Done)`。
- 每回合 message 数随失败重试增长（每次失败追加错误+重试提示约 2 条消息），输入 token 也随之膨胀。

### 3.5 个别“卡住”体感的来源

429 需要 **4-13 秒**才返回（本地代理在等上游判定，如 `5057ms / 9170ms / 12948ms / 14870ms`）。期间 TUI 状态为 `Streaming…` 且 `streaming_text_len=0`，用户看起来是“流式但不出字”，随后才进入重试退避：

- 退避：`retry_backoff_delay`：1s 起步指数翻倍（`1s→2s→4s→8s…`），封顶 `retry_backoff_cap_secs=30`；若响应带 `Retry-After` 最多等待 60s。
- 一次失败“体感卡住”几十秒，一个回合耗 3-4 分钟很正常。

## 四、jcode 侧行为解释

- 429 在 `is_retryable_error` 中被明确判为可重试（正确）。
- `max_retries=8`、退避封顶 30s，最终通常能在 8 次内拿到 200，因此 `cross_provider_failover` 基本不触发。
- `providers.axonhub` 是自定义 `open-ai-compatible` 提供商，只有单一路由、单一账号：`same_provider_account_failover` 对它不生效，只能反复打同一个 8090。
- 无传输层错误（无 timeout / refused / reset / TLS 错误），网络配置无问题。

---

## 五、建议

1. **主因在上游配额**：免费模型（`mscope/st/gitee/ocfree`）共享限流额度。去 axonhub 后台/文档确认当前 API key 的 QPS 与并发上限，高峰期错峰或改付费档位。
2. **换模型收益有限**：当前默认 `mscope/glm-5.2`（56% 失败）可切到 `st/deepseek-v4-flash`（48% 失败）略微改善，但都解决不了根本。
3. **升级 axonhub**：当前 `1.0.0-beta6`（改动日志很短），关注新版是否改进 429 处理、支持多 key / 多上游负载分摊。
4. **jcode 侧可调参数**（`~/.jcode/config.toml` `[provider]`）：
   - `retry_backoff_cap_secs`：30 → 60（匹配上游限流窗口，让重试打在窗口恢复后，减少空转）。
   - 保持 `max_retries = 8`、`stream_idle_timeout_secs = 180`。
5. **验证手段**：直接在 axonhub 上压测同一批请求，统计 429 占比与上述数据对照；观察晚间与凌晨的差异。
